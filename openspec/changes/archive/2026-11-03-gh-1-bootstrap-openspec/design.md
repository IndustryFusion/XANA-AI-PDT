# Design

## Context

See proposal.md - Why. The repository currently holds only documentation
(`README.md`, `manifest.md`, `architecture.md`, `LICENSE`); `architecture.md`
describes backend, frontend and Helm components that are not yet in the
repository. There is no CI. The plan was agreed on issue #1.

## Goals / Non-Goals

**Goals:**
- Use OpenSpec's native schema, commands and skills; add only configuration,
  instructions and documentation around them.
- Keep specifications agent-independent; agent-specific files are generated by
  `openspec init` and point at shared instructions.

**Non-Goals:**
- Custom OpenSpec schemas or tooling.
- Seeding `openspec/specs/` from `architecture.md` (possible follow-up issue).

## Decisions

**Default `spec-driven` schema.** Its proposal → specs → design → tasks
artifacts already separate requirements (specs) from implementation decisions
(design, tasks). Alternative: a custom schema with an explicit approval
artifact; rejected as unnecessary infrastructure.

**One Pull Request per change, gated by a `spec-approved` label.** The agent
first pushes only `openspec/changes/<id>/`; maintainers review and add the
label; implementation commits follow in the same PR. Alternative: separate
spec and implementation PRs; rejected by maintainers as extra overhead. Spec
and code commits stay distinguishable in history.

**Traceability by naming and a proposal line.** Change IDs
`gh-<issue>-<kebab-summary>` plus `Issue: #N` in `proposal.md`, enforced by
`openspec/config.yaml` rules and the PR template. Alternative: a GitHub
integration service; rejected (minimal infrastructure).

**`AGENTS.md` as the single instruction source.** It is read natively by most
coding agents; `CLAUDE.md` points to it. Claude Code is the starting agent and
gets native skills and `/opsx:*` commands; other agents are added later with
`openspec init --tools <id>`.

**CI installs a pinned, checksum-verified standalone binary.** The workflow
downloads the release asset for a fixed version from GitHub and checks its
SHA-256 before running it. Alternatives: piping the unpinned install script
(script content not pinned) or `npm install -g` (adds a Node toolchain).

**Project context references existing docs.** `openspec/config.yaml` context
summarizes `manifest.md`/`architecture.md` and links to them instead of
duplicating them, and states no code-level test or lint rules until the code
location is decided.

## Risks / Trade-offs

- [Anyone with triage rights can add `spec-approved`] → Documented as an open
  governance item; maintainers decide on CODEOWNERS and branch protection.
- [`architecture.md` describes code that is not in the repository] → Context
  marks it as the target architecture; agents must not assume the code exists.
- [Pinned OpenSpec version ages] → Bump version and checksum in one place in
  the workflow.
- [Green CI is not functional correctness] → Contributor guide lists the checks
  that require human review.

## Open Questions

- Location of application code and its test/lint conventions (deferred by
  maintainers).
- Whether to enforce label permissions via CODEOWNERS and branch protection.

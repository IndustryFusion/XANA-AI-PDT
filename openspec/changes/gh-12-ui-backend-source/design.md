# Design

## Context

See proposal.md → Why. The UI data interface (`frontend/src/data/interface.js`, `frontend/docs/data-interface.md`) and its facade (`frontend/src/data/index.js`) were built for this step: a source is a set of area modules, selected by `VITE_DATA_SOURCE`, and screens cannot reach sources or the network directly (lint rules).

`gh-12-run-api` provides the endpoints, with snake_case fields and the error shape `{"error": {"kind", "message"}}`. `gh-12-backend-foundation` provides `/api/diagnostics` and the development proxy for `/api` and `/ws`.

The current spec `operator-ui/data-source` → Configurable data source says "exactly one data source". A backend source that delegates to the mock conflicts with that wording, so this change modifies the requirement (see proposal.md).

## Goals / Non-Goals

**Goals:**
- A thin adapter: transport, case mapping and error mapping, with no business logic.
- The whole UI stays usable in phase 1.

**Non-Goals:**
- Changing screens or the interface's operations.

## Decisions

### 1. Composite source
```
frontend/src/data/sources/backend/
  index.js       area modules: backend operations merged over the mock's
  http.js        fetch wrapper: base path, JSON, case mapping, error mapping
  runs.js        runs operations and subscribeRun
  incidents.js
  system.js      getHealth
  map.js         snake_case ↔ camelCase, the outbound files shape
```
`index.js` builds each area as `{ ...mock[area], ...backend[area] }`, so delegation is visible in one place. The facade registers it as `backend`. Mock dev controls keep working for the delegated areas.

*Alternatives:*
- A backend-only source where everything else rejects with `unavailable`: most screens would show error states in phase 1.
- Per-area source configuration: more flexible, but more settings than phase 1 needs.

### 2. Transport
- **REST:** relative paths (`/api/...`), so the development proxy works now and a production proxy works later. The prefix comes from `VITE_BACKEND_BASE`, default empty.
- **WebSocket:** `${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.host}/ws/run/{id}`.
- **Timeout:** 15 s per request. A timeout or network error becomes `DataError('unavailable')`.
- **Error mapping:** backend errors map kind to kind. Any other status maps as follows: 401/403 to `unauthorized`, 404 to `not_found`, 409 to `conflict`, 422 to `invalid`, everything else to `unavailable`.

### 3. Case mapping
Response keys are converted recursively from snake_case to camelCase, including inside step `input` and `output` and state `data` (the workflow emits snake_case there, too). Request keys are converted the other way. Only keys change; values, such as the operator's text, are never altered. This keeps the mapping in one function.

*Alternative:* have the backend emit camelCase. That would mix conventions in the Python code base, which `architecture.md` writes in snake_case (`run_id`).

### 4. Run stream
`subscribeRun(runId, onEvent)` works as follows:
1. Open the socket and forward `snapshot`, `step`, `status` and `error` events after case mapping.
2. When the socket closes unexpectedly, emit `{type: 'connection', state: 'reconnecting'}`.
3. Retry after 0.5 s, 1 s, 2 s, 4 s, then every 8 s. The new socket's first event is a snapshot, which replaces the screen's state.
4. On close code 4404 (unknown run), or when the server sends an `error` event, emit the error and stop.
5. If the socket closes before the first snapshot arrived (the backend cannot be reached), emit an `unavailable` error and stop, so the run view shows its error state with a retry instead of waiting forever.
6. Messages of other types, such as the backend's `keepalive`, are not forwarded.
7. `unsubscribe()` closes the socket and cancels retries.

### 5. Tests
- **Unit tests:** fake `fetch` and a fake `WebSocket` cover mapping, errors, delegation and the stream recovery sequence (using fake timers).
- **Interface tests:** the existing `tests/data/interface.test.js` shape checks run against the backend source, fed with recorded backend responses from `tests/data/backend-fixtures/`, regenerated by a script against the local backend.
- **End-to-end:** `frontend/e2e/backend/` covers start → steps → clarify → confirm → archive → history, a rejection round, escalation not offered, a run archived elsewhere, system health, and a backend that is stopped (requests to `/api` refused in the browser). A Playwright project runs it with `VITE_DATA_SOURCE=backend` on its own development server port; it is selected with `XANA_E2E_BACKEND=1` (`npm run test:e2e:backend`), so `npm run test:e2e` keeps running the mock project only.
- **Scripted provider:** the backend's `LLM_PROVIDER=scripted` answers with the agent package's `clarified` script: the first round asks a question, and a round after a clarification proposes a diagnosis. A scripted run then passes through every phase 1 state the UI shows, which the end-to-end tests and the fixture recording need.
- **CI:** the `Backend` workflow gains an `integration` job. It starts the local environment's `db`, `broker`, `sample-data` and `backend` services with the scripted provider (no model download), waits until the sample machine is in the broker and the run API answers, and runs the Playwright `backend` project. The workflow triggers on changes to `backend/**`, `frontend/src/data/**`, `frontend/e2e/backend/**`, the Playwright configuration and the frontend package files.

*Alternative:* end-to-end against a stubbed backend only. That would not catch drift between the real backend and the adapter.

## Risks / Trade-offs

- **Mixed data in phase 1:** areas on the mock show sample data next to the backend's real runs. Mitigation: the sample machine identifiers are shared (`gh-12-backend-foundation`, decision 10), and `data-interface.md` lists which operations come from where.
- **Integration job duration:** starting the broker takes about a minute. This is accepted for confidence; the job runs only on relevant paths.
